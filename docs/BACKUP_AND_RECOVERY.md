# النسخ الاحتياطي والاستعادة (Backup & Recovery)

هذه الوثيقة جزء من متطلبات Phase 16 (الأمان + الاختبارات + النسخ الاحتياطي) — تحدد
بوضوح ما يُنسخ احتياطيًا، بأي تكرار، وكيف تتم الاستعادة عند الحاجة.

## 1. ما الذي يحتاج نسخًا احتياطيًا؟

| العنصر | أين يعيش | آلية النسخ الاحتياطي الحالية |
|---|---|---|
| قاعدة البيانات (كل شيء: شركات، مستخدمون، مستندات، مدفوعات...) | Supabase Postgres | `.github/workflows/backup.yml` (يومي) — راجع §2 |
| إثباتات الدفع المرفوعة (Payment.proofData) | داخل جدول `Payment` في نفس قاعدة البيانات (Bytes column) | **مشمولة تلقائيًا** ضمن نسخة قاعدة البيانات نفسها — لا تخزين خارجي منفصل يحتاج نسخًا مستقلًا (قرار Phase 14 المتعمَّد) |
| الكود المصدري | GitHub (`mwsfaty-afk/makhzani`) | Git نفسه هو النسخة الاحتياطية — كل تاريخ التغييرات محفوظ |
| متغيرات البيئة / الأسرار (`.env`, مفاتيح PayPal، NEXTAUTH_SECRET...) | Vercel Environment Variables + ملف `.env` محلي **غير مرفوع لـ Git أبدًا** | راجع §4 — لا يوجد نسخ احتياطي آلي لهذه؛ التوثيق هو خط الدفاع |
| ملفات Migration (بنية قاعدة البيانات) | `prisma/migrations/` في Git | مشمولة ضمن نسخ الكود المصدري |

**ملاحظة مهمة**: Supabase **Free Tier لا يوفر نسخًا احتياطية تلقائية** (متاحة فقط من خطة
Pro USD 25/شهر فصاعدًا، مع Point-in-Time Recovery من خطة Team). بما أن هذا المشروع على
الأرجح على الخطة المجانية حاليًا، فإن `.github/workflows/backup.yml` **هو** آلية النسخ
الاحتياطي الفعلية والوحيدة — وليس إجراءً احتياطيًا إضافيًا فوق ميزة مدفوعة.

## 2. آلية النسخ الاحتياطي الحالية

- **الأداة**: `scripts/backup-database.sh` (يستخدم `pg_dump` عبر `DIRECT_URL`، صيغة
  `--format=custom` القابلة للاستعادة الانتقائية لجدول واحد عند الحاجة).
- **الجدولة**: `.github/workflows/backup.yml`، يوميًا الساعة 3:00 صباحًا UTC، بالإضافة
  إلى إمكانية تشغيل يدوي فوري (`workflow_dispatch`) من تبويب Actions في GitHub.
- **مكان التخزين**: GitHub Actions Artifacts (ضمن نفس المستودع، لا يحتاج حساب تخزين
  خارجي إضافي — أبسط حل بدون بنية تحتية جديدة).
- **الاحتفاظ (Retention)**: 30 يومًا لكل نسخة، ثم تُحذف تلقائيًا من GitHub.
- **الإعداد المطلوب مرة واحدة**: أضف سر `DIRECT_URL` في إعدادات المستودع
  (Settings → Secrets and variables → Actions → New repository secret) بنفس قيمة
  `DIRECT_URL` الموجودة في `.env`. **لا تضع القيمة الفعلية في أي ملف داخل Git أبدًا.**

### تشغيل نسخة احتياطية يدوية محليًا

```bash
DIRECT_URL="postgresql://...المنفذ-5432..." ./scripts/backup-database.sh
```

يتطلب `pg_dump` مثبَّتًا محليًا (`postgresql-client` على Linux، PostgreSQL.app/`brew
install libpq` على macOS، أو حزمة PostgreSQL على ويندوز).

## 3. إجراء الاستعادة (Restore Procedure)

1. **لا تستعد مباشرة فوق قاعدة الإنتاج الحية** إلا في حالة كارثة فعلية مؤكَّدة (فقدان
   بيانات، تلف قاعدة البيانات). أولًا استعد إلى مشروع Supabase جديد مؤقت للتحقق من سلامة
   النسخة.
2. نزّل ملف `.dump` المطلوب من GitHub Actions (تبويب Actions → اختر التشغيل → Artifacts).
3. شغّل:
   ```bash
   DIRECT_URL="postgresql://...قاعدة الاستعادة..." ./scripts/restore-database.sh path/to/makhzani_TIMESTAMP.dump
   ```
4. بعد الاستعادة، شغّل `npx prisma migrate deploy` للتأكد أن حالة الـ migrations متطابقة
   (احتياطي فقط — `pg_dump --format=custom` يشمل بنية الجداول فعليًا، فهذه خطوة تحقق لا
   خطوة إلزامية عادةً).
5. تحقق من سلامة البيانات: عدد الشركات، عدد المستخدمين، آخر معاملة — قبل توجيه التطبيق
   الفعلي (`DATABASE_URL`/`DIRECT_URL` في Vercel) لقاعدة البيانات المستعادة.
6. حدِّث متغيرات البيئة في Vercel لتشير لقاعدة البيانات الجديدة (إن تغيّر المضيف)، أو
   استعد داخل نفس المشروع مباشرة إن كان ذلك ممكنًا (Supabase → Database → Restore).

## 4. استراتيجية استعادة الأسرار (Secrets Recovery)

لا يوجد "نسخ احتياطي" فعلي للأسرار (`NEXTAUTH_SECRET`, `PAYPAL_CLIENT_SECRET`,
`DATABASE_URL`...) — بدلًا من ذلك:

- **`.env.example`** (مرفوع في Git، بدون قيم حقيقية) يوثّق **كل** متغير بيئة مطلوب، بحيث
  لا يُنسى أي متغير عند إعادة بناء البيئة من الصفر.
- **`NEXTAUTH_SECRET`**: يمكن توليد قيمة جديدة دائمًا (`node -e
  "console.log(require('crypto').randomBytes(32).toString('hex'))"`) — **لكن** توليد
  قيمة جديدة يُبطل كل جلسات NextAuth الحالية (كل المستخدمين يُسجَّلون خروجًا)، وأيضًا
  جلسات أدمن المنصة (تستخدم نفس السر). ليس كارثيًا، لكن يجب توقعه.
  **يُنصح**: احتفظ بنسخة من القيمة الحالية في مدير أسرار (1Password/Bitwarden) قبل أي تغيير.
- **مفاتيح PayPal / Supabase**: تُستعاد من لوحة تحكم كل خدمة مباشرة (PayPal Developer
  Dashboard، Supabase Project Settings → Database) — لا حاجة لنسخ احتياطي منفصل، فهي
  مُدارة بالفعل من مزوّد خارجي موثوق.
- **التوصية العامة**: احتفظ بنسخة من `.env` الكامل (القيم الحقيقية) في مدير أسرار
  مؤسسي (1Password Vault مشترك، أو Vercel/GitHub Secrets نفسها كمصدر وحيد للحقيقة) —
  وليس في أي ملف محلي غير مُدار.

## 5. خطة التعافي من كارثة (Disaster Recovery)

| السيناريو | الإجراء |
|---|---|
| حذف بيانات عرضي (Bug أو خطأ بشري) | استعادة جدول واحد فقط من آخر نسخة (`pg_restore --format=custom` يدعم استعادة انتقائية بـ `-t <table>`) بدل استعادة كاملة |
| تلف/فقدان مشروع Supabase بالكامل | إنشاء مشروع Supabase جديد → استعادة كاملة من آخر نسخة GitHub Actions Artifact → تحديث `DATABASE_URL`/`DIRECT_URL` في Vercel → `prisma migrate deploy` → إعادة تشغيل Deploy |
| فقدان الوصول لحساب Vercel | الكود بالكامل في GitHub، يمكن ربط مشروع Vercel جديد بنفس المستودع خلال دقائق؛ فقط أعد إدخال متغيرات البيئة (§4) |
| فقدان `NEXTAUTH_SECRET` تمامًا | ولّد قيمة جديدة (يُسجّل الجميع خروجًا مرة واحدة، لا فقدان بيانات) |
| تسريب/تسريب مشتبه به لأي مفتاح (PayPal Secret، DB password...) | أبطل المفتاح فورًا من لوحة تحكم المزوّد وولِّد بديلًا — لا علاقة بالنسخ الاحتياطي، إجراء أمني منفصل وعاجل |

## 6. الحد الأدنى المطلوب قبل الإطلاق الفعلي على Production

- [ ] إضافة سر `DIRECT_URL` في GitHub Actions (§2) — بدون هذا الـ Workflow لن يعمل.
- [ ] تشغيل نسخة احتياطية يدوية واحدة على الأقل (`workflow_dispatch`) والتحقق من نجاحها.
- [ ] تجربة استعادة كاملة مرة واحدة على مشروع Supabase تجريبي (وليس فقط قراءة هذه
      الوثيقة) — نسخة احتياطية لم تُختبر استعادتها لا تُعتبر نسخة احتياطية موثوقة.
- [ ] التفكير الجاد في الترقية لخطة Supabase Pro قبل استقبال بيانات عملاء حقيقيين —
      Point-in-Time Recovery ونسخ Supabase المُدارة أكثر موثوقية من `pg_dump` يدوي/مجدول
      لحالات الكوارث الحرجة زمنيًا (RPO أقل بكثير من 24 ساعة).
